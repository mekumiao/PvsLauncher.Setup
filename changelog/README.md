# 更新日志目录

`publish.ps1` 用它记录每个版本的变更与基线，**请勿手工修改 `state.json` 的提交哈希**，除非你清楚后果。

## 文件说明

| 文件                | 作用                                                                 |
| ------------------- | -------------------------------------------------------------------- |
| `v<版本>.md`        | 单个版本的更新明细，同时作为 GitHub Release 的正文。                 |
| `state.json`        | 每个发布版本对应的各仓库 HEAD 提交，用于计算“上一版本之后”的增量。   |
| `../CHANGELOG.md`   | 由 `state.json` 渲染的索引表，最新版本在前。                         |

## 基线规则

- 发布 `vX.Y.Z` 时，`publish.ps1` 取 `state.json` 中**小于 X.Y.Z 的最高版本**作为基线，用
  `git log <基线提交>..HEAD` 采集各仓库提交。
- 每次发布成功后，会把当前各仓库 HEAD 写入 `state.json`，作为下一版本的起点。
- `1.1.14` 是首次播种的基线：只记录提交哈希，不生成日志，因此索引从下一个版本开始。
- `chore(release): ...` 这类发布提交会被排除，不会出现在下一版日志里。
- 某仓库工作区存在未提交改动时脚本只给出提示，**未提交的内容不会进入日志**。

## 手工干预

- **补录/修改某版本日志**：直接编辑 `changelog/v<版本>.md`，然后以 `-SkipBuild -Regenerate` 重跑会覆盖，请改用
  `-SkipBuild`（不带 `-Regenerate`）复用已有日志并重新发布 Release。
- **重发同一个版本**：默认复用已存在的日志与基线，GitHub Release 走更新逻辑，资产同名覆盖。
- **基线丢失**：若 `state.json` 中某仓库的提交在当前仓库不存在（例如历史被改写），脚本会回退到该仓库最新标签，
  再回退到首个提交，并在控制台给出警告。

## 相关环境变量

| 变量                             | 用途                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| `Github_PvsLauncherSetup_ApiKey` | GitHub 仓库内容读写权限，用于推送与创建/更新 Release。     |

Token 只从环境变量读取，脚本不会写入任何文件，也不会打印到控制台。
